# ADR-0002. Модульный монолит вместо слоистого

- **Статус:** принят
- **Дата:** 2026-10-10

## Контекст

Первая версия каркаса была слоистой: `Api → Application → Domain ← Infrastructure`, а фичи раскладывались папками внутри каждого слоя. У этого проекта есть особенности, которые на такой схеме неудобны:

1. **Части системы разной зрелости.** Ядро (дерево событий и задач) стабильно. ИИ-ассистент, интеграция с Google Таблицами (открытый вопрос, [ADR-0001](0001-task-table-source.md)) и Telegram-уведомления — эксперименты: их могут добавить, переписать или выбросить.
2. **Разным частям нужны разные зависимости.** Базе знаний — полнотекстовый поиск, ассистенту — LLM-клиенты и промпты, импорту — парсеры MD и xlsx, уведомлениям — Telegram-бот. В слоистой схеме всё это попадает в один проект `Infrastructure`, и он превращается в свалку.
3. **Команда маленькая, у каждого своя зона.** На хакатонах мы делили код на зоны, чтобы было меньше конфликтов. В слоистой схеме одна фича («база знаний») задевает четыре проекта плюс общий `DbContext` и общую папку эндпоинтов, поэтому конфликты неизбежны.
4. **Хостинг слабый.** Микросервисы нам не нужны: процесс должен быть один.

## Варианты

| | Слоистый монолит | **Модульный монолит** | Микросервисы |
|---|---|---|---|
| Где живёт фича | размазана по слоям | в одном модуле | в своём сервисе |
| Границы между частями | соглашение | `internal` + отдельные сборки + архитектурные тесты | сеть |
| Добавить или выкинуть экспериментальную часть | правки во всех слоях | добавить или удалить модуль | добавить или удалить сервис |
| Деплой | один процесс | один процесс | много процессов, брокер, наблюдаемость |
| Цена старта | минимальная | небольшая | высокая |

## Решение

Делаем **модульный монолит**: сначала режем систему вертикально, по бизнес-модулям, а слои остаются **внутри** модуля (папки `Domain` / `Application` / `Infrastructure` / `Endpoints`). Модули собираются в одно приложение (`Bootstrapper`) и разворачиваются одним контейнером.

### Модули

| Модуль | Отвечает за | Публичный контракт (`*.Contracts`) |
|---|---|---|
| **Identity** | пользователи, команды, участники, роли, приглашения, вход | текущий пользователь, проверка прав |
| **Planning** — ядро | дерево `Item` (макро / событие / группа / задача), свои поля и статусы, зависимости, ссылки, расписание, **ChangeSet** (предпросмотр и применение пакетов правок), история; запросы «Сегодня / завтра» и «Сводка» | чтение дерева, `ProposeChangeSet` / `ApplyChangeSet`, события (`ItemDeleted`, `TaskStatusChanged`, …) |
| **Knowledge** | MD-документы у узлов, вложения, полнотекстовый поиск | чтение документов узла и поддерева |
| **Interchange** | каноническая `TaskTable` и адаптеры: Markdown (сейчас), xlsx/csv, Google Таблицы (ADR-0001), iCal (позже), «контекст для ИИ» | экспорт поддерева в MD или контекст для ИИ |
| **Assistant** | провайдеры LLM, промпты, сессии, учёт токенов; ответы превращаются в ChangeSet с пометками «из текста / додумано» | — (его никто не вызывает) |
| **Notifications** *(позже)* | Telegram-бот: «задачи на завтра», дедлайны, назначения | — |

Чего **нет** среди модулей, и это намеренно:
- **Задачи, поля, статусы, «Сегодня», «Сводка» — внутри Planning.** Это одно связанное дерево. Если его разрезать, получится «распределённый монолит в миниатюре»: модули будут постоянно ходить друг к другу за данными.
- **Шаблоны событий** («хакатон на 4 дня») — это `TaskTable` без дат, значит, они живут в Interchange.

### Правила границ

1. Модуль видит у других модулей **только** их `*.Contracts`. Всё остальное объявляется `internal`, поэтому нарушение не скомпилируется.
2. Писать в дерево могут только Planning и, через него, `ChangeSet`. Interchange и Assistant **предлагают** ChangeSet, а не пишут в таблицы Planning. В итоге проверки, права, история и поиск конфликтов находятся в одном месте.
3. Одна база PostgreSQL, **своя схема на модуль** (`identity`, `planning`, `knowledge`, `interchange`, `assistant`), свой `DbContext` и своя история миграций. Между схемами не делаем ни JOIN, ни внешних ключей: модули ссылаются друг на друга только по Id.
4. Реакции на события («узел удалён → архивировать его документы») идут через внутрипроцессную шину событий из `BuildingBlocks`.
5. Правила 1–3 проверяют архитектурные тесты (`RoadmapPlusPlus.ArchitectureTests`) в CI.

### Граф зависимостей (только через Contracts)

```
Identity      ← все
Planning      → Identity
Knowledge     → Identity, Planning
Interchange   → Identity, Planning, Knowledge
Assistant     → Identity, Planning, Interchange
Notifications → Identity, Planning
```

Циклов нет. Ядро (Planning) не знает ни про ИИ, ни про форматы, ни про Google.

## Последствия

**Плюсы**
- Фича живёт в одной папке и у одного владельца. Конфликтов меньше, ревью проще.
- Открытый вопрос из ADR-0001 сводится к тому, добавить ли адаптер в Interchange. Ядро это не затрагивает.
- Экспериментальный модуль можно отключить флагом или удалить целиком.
- Если ассистенту понадобится отдельный процесс (длинные вызовы LLM, Ollama на другой машине), его можно вынести по уже готовой границе.

**Минусы и как их гасим**
- Больше проектов: по два на модуль вместо четырёх на всю систему. Contracts заводим, только когда у модуля появляется потребитель (у Assistant его нет).
- Нужна дисциплина вокруг событий и контрактов. Шину держим максимально простой: внутрипроцессная, без брокера.
- Риск растащить ядро по модулям. Правило: всё, что является частью дерева, остаётся в Planning.

## Когда пересматривать

- Если Planning вырастет так, что его неудобно держать одному-двум людям, делим его внутри на подмодули, но не выносим наружу.
- Если появится нагрузка, которой нужен отдельный процесс (ИИ, импорт больших файлов), выносим соответствующий модуль в сервис.
