# ADR-0003. Команды, роли и видимость событий

- **Статус:** принят
- **Дата:** 2026-10-13

## Контекст

Один человек живёт в нескольких командах сразу: команда на хакатон или учебная группа. При этом ему нужен один таймлайн, на котором видно всё, что касается его.

Внутри команды не всем нужно видеть всё. В большой команде у подгрупп свои события, и общий таймлайн забивается чужим. В маленькой команде (3–5 человек на хакатоне) разграничение только мешает.

В черновике доменной модели была одна роль на всю команду (`owner` / `editor` / `viewer`). Она отвечает на вопрос «кто может править», но не на вопрос «кто что видит». Личные роадмапы вне команд не были описаны.

## Варианты

| | Что это | Почему нет |
|---|---|---|
| Личные роадмапы + командные | у узла владелец — человек или команда | две модели владения: каждую проверку прав, выборку, импорт и ИИ пришлось бы писать в двух вариантах |
| Одна роль на всю команду | `owner` / `editor` / `viewer` | не разграничивает видимость событий внутри команды |
| Доступ к каждому узлу отдельному человеку | как «Поделиться» в Google Drive | при десятках событий и смене состава управлять невозможно |
| **Роли команды** | глава раздаёт роли, роли открывают события | — |

## Решение

### 1. Роадмапы только командные

- Каждый узел принадлежит ровно одной команде (`Item.workspaceId`). У узла и всех его потомков команда одна; перенести узел в другую команду нельзя.
- Отдельного личного роадмапа нет. Нужен личный — создаёшь команду из одного себя. Механизм один, исключений нет.
- Человек без команд видит пустой таймлайн и две кнопки: «Создать команду» и «У меня есть приглашение».

### 2. Участники и главы

- Участник (`Member`) — это пара «пользователь + команда». Один человек может состоять в любом числе команд, и в каждой у него свой набор ролей.
- **Глава** — признак участника (`Member.isHead`), а не одна из ролей: глава нужен и при выключенных ролях, и его права не зависят от привязок.
- Глава видит и правит всё в команде, приглашает и исключает участников, включает и выключает роли, создаёт роли, раздаёт их и открывает им события.
- Создатель команды становится главой. Глав может быть несколько. Последнего главу нельзя снять или исключить, и сам он не может выйти, пока не назначит другого.

### 3. Флажок «Включить роли»

У команды есть флажок `Workspace.rolesEnabled`, по умолчанию выключен.

| | Роли выключены | Роли включены |
|---|---|---|
| Обычный участник видит | все события команды | только события, открытые хотя бы одной из его ролей |
| Глава видит | всё | всё |
| Управляют командой | главы | главы |

- Выключение не удаляет роли и привязки: они перестают действовать, а при повторном включении возвращаются.
- При включении глава видит предупреждение: «N событий не открыты ни одной роли — их увидят только главы».

### 4. Роли

- Роль (`Role`) принадлежит команде: название и цвет. У участника может быть несколько ролей (`MemberRole`).
- Роль открывает узлы (`ItemRole`: узел + роль). Доступ действует на всё поддерево: открыл роли хакатон — ей видны его дни, группы, задачи, расписание и база знаний.
- Доступ складывается: узел виден, если он сам или любой его предок открыт хотя бы одной ролью участника. Запрещающих правил нет: «роль X скрывает событие Y» не бывает.
- Видеть значит работать: кому узел виден, тот может его править и создавать внутри него узлы. Отдельный режим «только просмотр» — открытый вопрос (см. ниже).

### 5. Предки и новые узлы

- Если участнику видно событие, но не видно макрособытие, в которое оно вложено, предок показывается **рамкой**: только название и даты, без описания, ссылок, базы знаний и других детей. Иначе событие висит на таймлайне без контекста.
- Узел, созданный внутри видимого узла, получает доступ от предка. Привязывать роли к каждой задаче не нужно.
- При включённых ролях узлы верхнего уровня создают только главы и сразу выбирают, каким ролям их открыть. Обычный участник создаёт узлы только внутри видимых ему.

### 6. Главный роадмап

- Главная показывает на одном таймлайне всё, что видно человеку, из всех его команд. У каждой команды свой цвет (`Workspace.color`); в панели события подписано, из какой оно команды; есть фильтр по командам.
- Все остальные экраны работают в тех же границах видимости: «Сегодня / завтра», поиск, база знаний, экспорт, «контекст для ИИ» и ассистент. ИИ не видит и не правит то, чего не видишь ты.
- Ответственным за задачу (этап 2) можно назначить только того, кому эта задача видна.

### 7. Где что живёт

По правилам [ADR-0002](0002-modular-monolith.md):

| Модуль | Что хранит |
|---|---|
| Identity | `Workspace` (название, цвет, `rolesEnabled`), `Member` (пользователь, `isHead`, цвет человека в команде), `Role`, `MemberRole`, приглашения |
| Planning | `Item.workspaceId`; `ItemRole` — какие роли открывают узел. Привязки лежат рядом с деревом, на роль ссылаются по Id без внешнего ключа между схемами |

- `Identity.Contracts` отдаёт доступ пользователя: список его команд и по каждой — глава ли он, включены ли роли, какие у него роли.
- Planning по этим данным сам решает, какие узлы видны, одним рекурсивным запросом. Все выборки дерева идут через одну функцию видимости, чтобы правило не расползлось по эндпоинтам.
- Если роль удалили, её привязки в Planning просто перестают совпадать с ролями участников. Убираем их, когда появится шина событий (этап 3).

## Последствия

**Плюсы**
- Одна модель владения: узел всегда в команде. Права, импорт, ИИ и таймлайн пишутся один раз.
- Доступ задаётся на уровне событий, задачи и расписание наследуют его сами.
- Маленькая команда не замечает ролей: флажок выключен, все видят всё.
- Главная страница отвечает на вопрос «что у меня в этом году» сразу по всем командам.

**Минусы и как их гасим**
- Каждый запрос к дереву фильтруется. Держим одну функцию видимости и покрываем её тестами на все случаи из таблицы раздела 3.
- Рамки предков усложняют таймлайн. Рамка — тот же блок без содержимого, отдельного вида узла не заводим.
- Главы — единственные, кто управляет командой. Для небольших команд этого достаточно; права «модератора» добавим, если понадобятся.

## Открытые вопросы

- Нужен ли режим «только просмотр» (менторы, жюри). Если да — поле `access` (`view` / `edit`) у привязки `ItemRole`.
- Приглашение с заранее выданными ролями: ссылка «для жюри» сразу даёт роль «Жюри».
- Видит ли обычный участник состав команды и список ролей целиком или только свои.

## Когда пересматривать

- Понадобится скрыть часть поддерева внутри открытого события — придётся вводить запрещающие правила.
- Понадобится одно событие на несколько команд (совместный хакатон двух СКБ) — придётся разрешить узлу принадлежать нескольким командам.
